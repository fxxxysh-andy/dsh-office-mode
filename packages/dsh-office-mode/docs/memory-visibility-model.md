# 办公记忆的可见性与权限模型

第十九轮 P2-10（档案编号 `19-7`）的研究交付：**多用户 / 多 Agent 的可见性与访问控制语义**。
原文的口径是「先模型后实现，不开可写端点」—— 这份文档就是那份**模型**，第五十四轮落地的是
它在**读侧**已经成立的那一半（`新-12` 的分区与 `read` / `status` 的自述），写入侧只保留既有的
两道质量门，**没有**新增任何权限端点。

状态口径（照实写）：**模型已定；实现覆盖读侧、既有的写入期质量门，以及第八十轮的按次写入范围
（`scope` 参数）**；下面「明确不做」一节列的几项没有实现，也不打算在近期实现。

---

## 1 一句话

这套记忆里**没有「用户身份」这个概念**。可见性是**四个已经存在的维度**的乘积 ——
哪个根、哪个目标、哪个分区、哪个来源档 —— 加上**三个执行点**（自动投影 / 显式读 / 写入期质量门）
上的判据。任何「谁能看到什么」的问题，都能拆成「落在哪个根 × 哪个目标 × 哪个分区 × 哪个档」来回答。

## 2 谁在看（actor）

| actor | 看得到什么 | 怎么拿到 | 对应的执行点 |
| --- | --- | --- | --- |
| 主会话的模型 | 自动投影里的热记忆与最近台账；显式 `read` 的结果 | `office_help` / `office_run` 的反馈末尾；`office_memory({action:'read'})` | ① 自动投影 ② 显式读 |
| 用户 | 全部（含被投影折叠掉的条目） | 记忆浏览面板（`/office-memory/snapshot`）、`USER.md` / `MEMORY.md` / `archive/*.md` | 面板的可见范围见 §4 |
| 检索子代理 | **只有白名单工具**（`CHANNEL_TOOLS`），但它拿得到工作目录 | `office_search_dispatch` 派工 | ③ 派工的工具掩码 |
| 另一个工作目录 | 只读得到**全局根**（`scope` 为 `global` / `both` 或 `userScope:'global'` 时） | 自己的会话 | ① ② |
| 外部（Pack 文件） | 导出包里有什么就有什么 | `export` / `import` | ④ 导入的档位合并 |

## 3 看什么（resource）

| 资源 | 归类字段（分区用） | 备注 |
| --- | --- | --- |
| 热记忆条目（`memory.json`） | `tags` / `entities`（`target` 与 `importance` **不参与分区**，它们只影响容量与排序） | 会被自动投影，所以是可见性最敏感的一处 |
| 台账行（`ledger.jsonl`） | `theme`（没有实体） | 记的是「产出过什么、用过哪些来源」 |
| 归档条目（`archive/*.jsonl`） | 热记忆下沉的带 `tags` / `entities`；台账滚下来的只有 `theme` | 只读、参与召回 |
| kb 文档与块 | `path`、来源档 `tier` | 存的是**来源原文**，不是结论 |
| 关系边（`links.jsonl`） | 端点 id | 悬空引用恒为 0 是不变量 |
| Pack | 整包 | 只增不改、按 id 幂等 |

## 4 四个维度（可见性的开关）

### 4.1 根（哪一份存储）

`memory.scope` = `workspace` | `global` | `both`，`memory.userScope` = `memory` | `global`
（`src/memory.js` 的 `MEMORY_SCOPES` / `USER_SCOPES`、`buildStores()`）。

- 写：`target:'user'` 在 `userScope:'global'` 时落全局根，其余按 `scope` 落；台账这类
  「项目产物」落工作区根（`defaultStore()`）。
- 按次覆盖（第八十轮）：`add / replace / remove / kb-ingest / kb-drop` 可带
  `scope:'workspace'|'global'`，本次只读写那一个根；该根没被设置打开就报错，不会退到
  默认根。显式 scope 下的 replace / remove 也**不跨根兜底** —— 找不到就如实报错，
  避免「以为改了全局、实际改了工作区」。它不改变读的可见范围。
- 读：**所有根一起读**，全局根在前、工作区根在后 —— 顺序就是优先级：具体项目的约定
  覆盖通用偏好。来自全局根的行标「（全局）」，未标的是工作区根。
- 知识库是**单库**（第八十八轮）：它不跟着记忆根分 global / workspace，始终落在
  `memory.kbDir`（默认 `$DSH_HOME/.office/kb`，相对路径相对用户主目录）。因此
  `kb-ingest` / `kb-drop` 的 `scope` 参数只为旧调用面保留，**不再选根**；要按项目分档
  用虚拟文件夹 `folder`，而不是第二座库。知识库的墓碑也落在库目录里。
- 记忆根仍是唯一一个真正意义上的「跨项目共享」开关：**没有它，另一个工作目录看不到
  热记忆 / 台账 / 归档**（知识库不受它影响，因为只有一座）。
- 归档根按**真实工作区身份**隔离（多工作区旧档碰撞）：共享同一 `memoryDir` 时，新档写
  `archive/workspaces/<key>`（key 来自规范 realpath 摘要），独占目录仍写
  `<memoryDir>/archive`；同一物理目录的符号链接 / `..` 归一到同一身份。旧档只有在目录内
  （owned）或存在显式 `archive/workspace-owner.json`（claimed）时才可读；未归属旧档不投影到
  知识库、浏览或读取，只在 `status.archiveScope` 留一条不含文件名、正文或绝对路径的警告。
  读取、浏览与状态查询都不改写任何归属证据。
- **显式 `memory.globalDir` 的归属无法仅凭路径核实**：保留原路径与旧档读取，但
  `archiveKeep` 的保留上限跳过删除，`status.archiveScope` 给出「显式配置、归属无法核实」
  的警告；默认专用全局路径（未配 `globalDir`）仍正常执行保留上限。若调用方已知兄弟工作区
  的 archive，或目录内有 `workspace-owner.json`，则按共享 / 工作区处理，风险保护优先。
- **只读碰撞不持久化归属**：一次只发生读、浏览或状态查询的目录碰撞，不会写
  `workspace-owner.json` 或全局归档标记；全局归档标记只在一次成功的真实归档写入之后出现，
  空写、失败写、只读与推断都不建立。因此后续仍按「归属未知」保守处理，而不是把共用旧数据
  自动分给某个库。

### 4.2 目标（`target`）

`user`（用户偏好与要求）/ `project`（项目事实与约定）。两者都进自动投影与显式读；
容量上限各自独立（默认 4096 / 10240 字节）。

### 4.3 分区（`tags` / `entities` / `theme`）

第五十四轮 `新-12` 落地的读侧**硬隔离**：`read` 给了 `tags` / `entities`，就只出
**显式声明过**这些标签 / 实体的条目（正文里出现不算）。同一个维度里给多个词是**合取**。

各层用自己的归类字段：热记忆与归档条目看 `tags` / `entities`，台账行看 `theme`（且
台账没有实体）。这是「一个工作目录一份记忆、里面混装多主题」时的隔离手段 —— 也是
`不引入第二套存储` 的前提下能做到的最强隔离。

### 4.4 来源档（`tier`）

kb 文档级：`user`（用户提供）/ `verified`（≥2 独立来源）/ `unverified`（单源未核实）。
两处硬规则：

1. **写入期质量门**（第四十一轮）：`add` / `replace` 引用 unverified 的块会被**拒绝**
   —— 单源内容不得进入热记忆当依据（`assertRefsTrusted()`）。
2. **入库评估闸**（第五十四轮 `19-8` 的 P1-4b）：`kb-ingest` 声明 `verified` 时，
   正文里必须数得出 **≥2 个独立主机名**（去掉 `www.` 再比、单标签主机名不算）；数不出
   就拒绝入库（`assertIngestEvidence()`）。**幂等重入是例外**：内容与档位都没变的再次
   入库不判门（`keepingTier`）—— 门是向前的，不追历史。
   这道闸是**形状门**（挡自相矛盾与占位符），不是真伪门。
3. **台账侧标注**：`read` 台账那一层时**现算**每行引用的档位，把「待核」与「在 kb 里
   找不到」标出来（`ledgerTrustOf()`）—— 档位会变、块会删，所以判据必须在读的那一刻算，
   不能沿用登记时的快照。

4. 单库之后不再有「同一份内容在多个根里档位不同」；同一份内容以两条路径入库时
   仍是同一批块 id，档位按更保守的一侧合并（`strictestTier()`，回归用例 F4）。

## 5 三个执行点上的判据

### ① 自动投影（`office_help` / `office_run` 的反馈末尾）

- 只贴热记忆与最近几条台账的**变动**；按「本次在做什么」的话题信号筛，无关条目折叠成一行。
- 热记忆或台账指纹没变的段落**整段不输出**（不加标题、不写条数与 revision、不带用量行）——
  未变化的部分不是信息，是每次调用都在付的前缀税（第七十九轮）。
- 有四道节流：同一条正文一个会话只贴一次、投影字节预算、心跳重贴仍受预算约束、未变化整段不输出。
- **投影里出现的东西等于自动进入模型上下文** —— 所以这里是最该保守的地方：条目越短越具体越好。

### ② 显式读（`office_memory({action:'read'})`）

- 过滤器（时间窗 / 分区）**先于**打分生效；解析不出来就报错，不静默忽略。
- 分区是硬过滤，关键词是排序键；两层语义不混。
- 回执首部自报口径（时间窗、范围、分区），所以「为什么这次没给某条」是可以核对的一句话。

### ③ 派工（检索子代理）

`office_search_dispatch` 给子代理一份**工具白名单**（`src/search.js` 的 `CHANNEL_TOOLS`：
`office_web_search` / `office_web_fetch` / `read` / `read_image` / `write`），
用白名单而不是黑名单：以后装进 profile 的新工具不会悄悄出现在子代理手上。

**如实记的边界**：白名单里有 `read`，而子代理的工作目录就是会话工作目录 ——
所以**它读得到 `.office/memory/` 下的文件**（只要模型让它去读）。工具掩码挡的是
「子代理拿到记忆工具」，不是「子代理能看到那个目录」。这条边界在派工提示里以
「把资料查回来、把结果写下去」的职责约束出现，属**约定**而非强制。

### ④ 导入（Pack）

- 只增不改、按 id 幂等；块正文与 id 对不上就整份拒收。
- 档位按**更保守**的一侧合并（本地说 unverified，包里的 verified 抬不动它）。
- Pack 与盘上的文件是**同一信任级**：能改文件的人就能改包。插件承诺的是**一致**，不是防伪造。

## 6 面板（用户侧）的可见范围

一级只有「记忆 / 知识库 / 图谱」三页；「个人偏好 / 项目记忆 / 台账」是记忆页内部的二级
分段，不再有「来源（全部 / 全局 / 工作区）」筛选行。个人偏好只收 `target:'user'`，写入时
有全局根就落全局；项目记忆收其它 target，只落当前工作区。这样全局不会被项目事实填满。
一级页签只写去处、不写条数：记忆是条、知识库是篇、图谱是边，三种单位不放在同一条轴上；
条数分别由二级分段、知识库区块头、图谱工具条回答。知识库是单库，页签上没有来源三档。

面板的写入是**直接写**：页内「直接记一条」填文字后 POST `/office-memory/mutate`
（`memory-add`），不再生成待发送指令；目标按钮显示「个人偏好（全局）」或「项目记忆
（本工作区）」，并跟随当前二级档切换默认值。知识库页的「＋上传文件」/ 拖放走
`POST /office-memory/kb-upload`，服务端只留切片与图片，原文件不进库。知识库文档可直接
删除（确认后 `kb-drop`，删整篇并清关系），块详情可建 / 解块间关系（`kb-link` /
`kb-unlink`）；上传件没有源文件，仍不允许改正文，只能删后重传。

`/office-memory/snapshot` 的可见根有**三个来源**（不是「本进程跑过办公工具的那一个」）：
本进程见过的工作区、工作区登记表、会话史（`src/view.js` 的 `knownWorkspaces()` /
`sessionWorkspacesOf()` 与路由里的错误文案都写明三条）。只读、非 GET 一律 405。

面板与**自动投影**的台账行只给「路径 / 格式 / 主题 / 用途」—— 依据（`kbRefs`）与
待核警告只在**显式 `read`** 的回执里印。这是有意的不对称：投影与面板的职责是
「有没有、在哪」，判断依据的强弱要在检索那一侧做。

## 7 明确不做（设计边界，别再当欠账）

| 项 | 为什么不做 |
| --- | --- |
| 多用户身份 / 登录 | 本插件跑在单用户的会话进程里，没有身份来源可依 |
| ACL / 角色 / 权限表 | 没有身份，权限表只能建在「工作目录」这一个主体上；四个维度已经覆盖了这个粒度的需求 |
| 授权撤销 / 分享链接 | 属可写端点（原文明确「不开可写端点」）；真要做先从「谁能写这个文件」那条链开始 |
| 审计日志 | 读不写盘是这套东西依赖的性质（面板、只读探针、真库对照都靠它），记 `lastAccessAt` 会把读变成写 |
| 跨工作区检索 | 全局根已经覆盖「跨项目共享」这一需求；再开一条会同时破坏隔离与容量口径 |
| 内容级加密 / 抹除 | 与「记忆是可 grep 的 Markdown + jsonl」这条可核对性冲突 |

## 8 什么时候该重开这一条

三个条件**同时**成立时：① 出现了第二个真实的写者（不是你自己的另一个工作目录）；
② 需求落在「同一条记忆对不同主体要不同答案」上，而不是「同一主体要更好的召回」；
③ 有一个可用的身份来源。缺任何一条，重开都会做出一套没人用的权限表。
